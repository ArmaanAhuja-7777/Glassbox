# Upgrade later

Things we deliberately deferred: what we do now, what to do later, and what should trigger the change. Review this list at the end of every phase, and before anyone else joins the project.

| # | Item | Now | Later | Trigger | Added |
| --- | --- | --- | --- | --- | --- |
| 1 | **Branch protection on `main`** | Free GitHub plan: private repos can't use branch protection or rulesets. CI runs on every PR, and we follow the rule "merge only when green, never push to `main` directly". | Upgrade to **GitHub Pro** (about $4/month) and require the `CI` checks (`Lint, typecheck, unit tests, build` and `End-to-end (Playwright)`) before merging; disallow direct pushes and force pushes to `main`. | Before a second person gets write access, or earlier if a red PR is ever merged by accident. | 26 Oct 2026 · phase 1 step 10 |
| 2 | **Node 26 LTS** | Repo pins Node 24 (`.nvmrc`, `engines >=24.11`, `@types/node` 24) because Node 26 wasn't LTS yet. | Switch `.nvmrc` to 26, update `engines`, `@types/node` and the Docker base image, run the full suite. | Node 26 shows "Active LTS" on https://nodejs.org/en/about/previous-releases. | 26 Oct 2026 · phase 1 step 1 |
| 3 | **TypeScript 7 (native compiler)** | Pinned to TypeScript 6.0.x: TS 7's JavaScript API is only published as `typescript/unstable/*`, and typescript-eslint supports `<6.1`. | Move to TS 7 (much faster type-checking) once its programmatic API is stable and typescript-eslint supports it. Phase 5 depends on the compiler API, so check that first. | TS 7 API marked stable, and typescript-eslint's peer range includes 7. | 26 Oct 2026 · phase 1 step 3 |
| 4 | **Split web tsconfig (app vs Node)** | `apps/web/tsconfig.json` includes both browser code and `vite.config.ts`, with `types: ["vite/client", "node"]`, so browser code could type-check against Node-only APIs like `process`. | Split into `tsconfig.app.json` (DOM only) and `tsconfig.node.json` (config files), and make sure typescript-eslint's project service still finds both. | When the web app grows beyond the version page (phase 2), or the first time Node types cause a bug. | 26 Oct 2026 · phase 1 step 6 |
| 5 | **CI tests the PR head, not the merge result** | CI checks out the PR's head commit so the displayed SHA matches the PR. It doesn't test the merge with the latest `main`. | With branch protection (item 1), enable "Require branches to be up to date before merging", or add a merge-queue / merge-commit test job. | Together with item 1. | 26 Oct 2026 · phase 1 step 10 |
| 6 | **Narrow Turbo `build` inputs** | Changing a test file also invalidates the package's `build` cache (Turbo hashes all package files). | Add `"inputs": ["$TURBO_DEFAULT$", "!src/**/*.test.ts", "!src/**/*.test.tsx"]` to `build` tasks. | When builds get slow enough for this to matter. | 26 Oct 2026 · phase 1 step 4 |
| 7 | **Shared Turbo remote cache in CI** | Each CI run rebuilds from scratch (only the pnpm store is cached). | Add a remote cache (self-hosted or Vercel's) so CI and laptops share build results. | When CI time per push exceeds about 5 minutes. | 26 Oct 2026 · phase 1 step 10 |
| 8 | **Make the repository private again** | Public, because Actions were blocked on the private repository by an account billing issue. | Resolve the GitHub billing issue, add spending budgets so metered usage can't block Actions again, then switch to private. Branch protection then needs GitHub Pro (item 1). Confirm CI still starts after switching. | When the owner judges the code proprietary enough to protect; at the latest before external design partners (phase 45). | 26 Oct 2026 · phase 1 step 10 |
